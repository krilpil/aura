# Архитектура проекта

Проект использует Feature-Sliced Design (FSD): код разделяется по ответственности на слои, внутри них — на слайсы и сегменты.

Документ описывает общие принципы, границы модулей, размещение кода и работу с сервером. Общие правила действуют вместе с уточнениями для конкретных слоёв; исключения указаны в соответствующих разделах.

## Основные принципы

### Читаемость и обработка ошибок

Во всём проекте главный приоритет — легко читаемый код: понятные имена, последовательная логика и простые условия.

- Длинные и объёмные функции нежелательны. Их следует разделять на небольшие функции с понятными именами, каждая из которых решает одну связную задачу и легко читается и проверяется отдельно. Декомпозиция должна следовать смысловым шагам алгоритма и упрощать понимание кода.
- Вложенные тернарные выражения запрещены. Для нескольких ветвей используются `if` с ранними возвратами или отдельная функция с понятным названием.
- Длинные цепочки проверок в одном условии запрещены. Смысловые части условия выделяются в именованные переменные или функции, объясняющие назначение проверки.
- Избыточные и повторные проверки без конкретной причины запрещены. Каждая проверка должна обеспечивать бизнес-ограничение или обрабатывать реально возможное состояние. Необходимая валидация внешних данных сохраняется.
- Для обработки асинхронных операций и их ошибок всегда используются цепочки `.then(...).catch(...)` вместо `try/catch`.

### Использование `as const`

Во всех слоях не следует использовать `as const` без конкретной необходимости. Предпочтительны стандартный вывод типов и контекстная типизация. Const assertion допустим, когда требуется сохранить литеральные типы, readonly-свойства или тип кортежа, а обычный вывод типов не обеспечивает нужный контракт. Не добавлять `as const` механически или для подавления непонятной ошибки типизации.

### Размер TSX-файлов

Во всех слоях следует стремиться держать каждый `.tsx`-файл в пределах 150 строк. Это ориентир для поддерживаемости кода, а не жёсткий запрет.

Если файл превышает 150 строк, нужно пересмотреть декомпозицию: выделить компоненты в отдельные `.tsx`-файлы, функции и хуки — в `lib`, типы — в `model` там, где предусмотрены эти сегменты. При разделении соблюдать ответственность слоёв FSD, правила вложенности директорий и размещения стилей.

## Архитектурная организация

### Слои и зависимости

Слои перечислены сверху вниз. Код может импортировать модули только из нижележащих слоёв.

| Слой | Назначение |
| --- | --- |
| `app` | Инициализация приложения, маршрутизация, провайдеры и глобальные стили. |
| `screens` | Полноценные экраны, собранные из виджетов, фич и сущностей. |
| `widgets` | Компоненты со сложной логикой или блоки, объединяющие несколько фич и координирующие их работу. |
| `features` | Компоненты, каждый из которых решает одну пользовательскую задачу: вход, поиск, смена темы. |
| `entities` | Бизнес-сущности: пользователь, компания, заказ. |
| `shared` | Общие компоненты, утилиты и инфраструктура без привязки к бизнес-сценариям. |

Направление зависимостей: `app → screens → widgets → features → entities → shared`. Можно обращаться к любому слою ниже, пропуская промежуточные.

### Слайсы и сегменты

Слои `screens`, `widgets`, `features` и `entities` делятся на **слайсы** — модули по предметной области или задаче. Слайсы одного слоя не импортируют друг друга.

Внутри слайса код разделяется по назначению на **сегменты**:

- `ui` — компоненты интерфейса и их стили.
- `model` — типы и интерфейсы.
- `lib` — вспомогательные функции, хуки и Zustand-сторы.

Сегменты создаются по необходимости. Слои `app` и `shared` не делятся на слайсы и организуются по техническому назначению кода.

Пример структуры слайса:

```text
features/
└── ChangeTheme/
    ├── getProfile.ts
    ├── ui/
    │   ├── ChangeTheme.tsx
    │   ├── ThemeOption.tsx
    │   └── ChangeTheme.styles.tsx
    ├── model/
    │   └── changeTheme.types.ts
    └── lib/
        └── useChangeTheme.ts
```

## Публичные интерфейсы и импорты

У каждого слайса слоёв `screens`, `widgets`, `features` и `entities` должен быть ровно один `index.ts`, расположенный в корне слайса. Это единый публичный интерфейс слайса: через него реэкспортируются все экспорты из `ui`, `lib` и `model`, а также публичные хуки запросов сущности. Вложенные `index.ts` внутри слайса запрещены, в том числе в сегментах и директориях запросов.

Внешние потребители импортируют только из корня слайса. Прямые импорты его внутренних файлов запрещены. Внутри слайса используются относительные импорты конкретных файлов без обращения к собственному корневому `index.ts`, чтобы не создавать циклические зависимости.

Пример `features/ChangeTheme/index.ts`:

```typescript
export * from './ui/ChangeTheme';
export * from './ui/ThemeOption';
export * from './ui/ChangeTheme.styles';
export * from './lib/useChangeTheme';
export * from './model/changeTheme.types';
```

Внешний импорт из вышележащего слоя:

```typescript
import { ChangeTheme } from '@/features/ChangeTheme';
```

Для публичного хука запроса в корневом `index.ts` сущности используется прямой реэкспорт из файла запроса, например `export { useExample } from './api/example/example';`. Внутренняя функция запроса остаётся неэкспортируемой.

Единый публичный интерфейс не отменяет направление зависимостей между слоями и запрет импортов соседних слайсов. На `app` и `shared`, которые не делятся на слайсы, правило единственного `index.ts` не распространяется.

## Код внутри слайса

Сегмент определяет назначение кода. Ниже описаны правила размещения компонентов, типов и логики. Особенности структуры и поведения компонентов `entities` приведены [отдельно](#особенности-entities).

### Компоненты и стили в ui

В слоях `features`, `widgets` и `screens` в `ui` допускаются только файлы компонентов `*.tsx` и стилей `*.styles.ts` / `*.styles.tsx`. Вложенные директории запрещены: все файлы лежат непосредственно в `ui`.

- Главный `.tsx`-файл называется как компонент: `ChangeTheme.tsx` для `ChangeTheme`.
- Рядом могут находиться дополнительные компоненты в других `.tsx`-файлах, например `ThemeOption.tsx`.
- В одном `ui` допускается не более одного файла стилей (исключение для `entities` описано в [особенностях слоя](#особенности-entities)). Его имя повторяет имя главного компонента с учётом регистра: `ChangeTheme.styles.ts` или `ChangeTheme.styles.tsx`.
- Все стили, включая объявления `styled-components`, всегда выносятся в этот общий файл `.styles.ts(x)`. Стили внутри файлов компонентов не допускаются.
- Имена styled-components начинаются с `S`, например `SExample`. Тип пропсов называется как styled-компонент с суффиксом `Props`: `SExampleProps`.

Для стилизации и позиционирования используются сами styled-components и ссылки на них в селекторах: `${SComponent}`. Ручной `className` допускается только в исключительных случаях, когда обратиться к нужному элементу средствами styled-components невозможно. Это ограничение действует и для `className` в `.attrs()`. Внутренние классы сторонних библиотек используются только для элементов, недоступных через отдельный styled-component.

Не следует создавать обертки исключительно ради класса или позиционирования доступного целевого компонента. Если сторонний компонент сам создает DOM-обертку и передает класс вложенному элементу, для выбора его обертки можно использовать `:has(${SComponent})`.

Во всех слоях статические атрибуты и props компонентов задаются через `.attrs({ ... })` в styled-components, а не непосредственно в JSX. Для этого используется существующий styled-component либо создаётся новый через `styled(Component)` с именем, начинающимся с `S`, даже если дополнительных CSS-правил нет. Это относится и к DOM-атрибутам, включая `aria-*`, и к props библиотечных компонентов, например `size`, `color`, `placeholder` и `icon`.

Объявления размещаются в общем файле стилей компонента. Если в нём используется JSX, файл должен иметь расширение `.styles.tsx`. Динамические значения и обработчики событий продолжают передаваться через props в разметке.

Отдельные файлы типов компонентов размещаются в `model`, хуки и вспомогательная логика — в `lib`.

### Типы в model

В `model` разрешены только файлы `*.types.ts` и `*.types.tsx`, например `changeTheme.types.ts`.

Типы пропсов styled-components объявляются в `model/*.types.ts(x)` и импортируются в `.styles.ts(x)`. В файлах стилей типы не объявляются.

Пример типа в `model/example.types.ts`:

```typescript
export interface SExampleProps {
  $active: boolean;
}
```

Использование в `ui/Example.styles.ts`:

```typescript
import styled from 'styled-components';

import type { SExampleProps } from '../model/example.types';

export const SExample = styled.div<SExampleProps>`
  opacity: ${({ $active }) => ($active ? 1 : 0.5)};
`;
```

### Логика и состояние в lib

В `lib` размещаются вспомогательные функции и хуки. Отдельные файлы типов размещаются в `model`.

Zustand-сторы размещаются в `lib` соответствующего слайса, в файлах `*.store.ts`, например `entities/session/lib/account.store.ts`.

Типы состояния и действий стора объявляются в `model/*.types.ts` и импортируются в файл стора. Экспорты стора включаются в единственный корневой `index.ts` слайса согласно [правилам публичных интерфейсов](#публичные-интерфейсы-и-импорты).

Ограничения на использование сторов в компонентах сущностей описаны в разделе [«Особенности entities»](#особенности-entities).

### JSX и обработчики событий

Во всех слоях в JSX-разметке запрещены условия, вызовы функций и другие вычисления — как в содержимом элементов, так и в значениях props.

Простые тернарные выражения без вложенности, `&&`, форматирование, арифметика и вызовы `map` / `filter` выполняются до разметки внутри компонента. Результаты сохраняются в именованные переменные, которые затем используются в JSX. Для нескольких ветвей используются `if` с ранними возвратами или отдельная функция согласно [общим правилам читаемости](#читаемость-и-обработка-ошибок).

Обработчики событий также объявляются до разметки и передаются по ссылке: `onClick={handleClick}`.

Во всех слоях JSX-элементы, передаваемые через props, заранее объявляются в именованных переменных. Передавать JSX непосредственно в значении prop запрещено: вместо `icon={<CheckDoubleIcon />}` используется ссылка на переменную `readAllIcon`. Правило относится к любым компонентам в props, а не только к иконкам, и действует также внутри `.attrs()`.

Статические JSX-элементы объявляются на уровне модуля, вне функции компонента, а ссылки на них задаются через `.attrs()` соответствующего styled-component. Если элемент зависит от props или состояния, он объявляется внутри компонента до `return`, а в разметку передаётся ссылка на переменную, например `content={content}`.

Пример статического элемента в общем файле стилей `NotificationFilter.styles.tsx`:

```tsx
import styled from 'styled-components';
import { Button } from '@technology-frontend/ui';
import { CheckDoubleIcon } from '@technology-frontend/icons-react';

const SReadAllIcon = styled(CheckDoubleIcon).attrs({
  'aria-hidden': true,
})``;

const readAllIcon = <SReadAllIcon />;

export const SReadAllButton = styled(Button).attrs({
  icon: readAllIcon,
  htmlType: 'button',
})``;
```

Использование в файле компонента:

```tsx
import { SReadAllButton } from './NotificationFilter.styles';

export const NotificationFilter = () => {
  return <SReadAllButton>Прочитать все</SReadAllButton>;
};
```

Пример внутри компонента:

```tsx
const label = `Записей: ${count}`;
const content = isEmpty ? <span>Нет записей</span> : <RecordList records={records} />;

return (
  <div>
    {label}
    {content}
  </div>
);
```

## Особенности слоёв

Эти правила уточняют ответственность слоёв и дополняют общие правила сегментов и импортов.

### Особенности widgets

Виджет — компонент со сложной логикой либо блок, который собирает несколько фич, связывает их данные и обработчики и управляет их взаимодействием.

В виджетах разрешены запросы через экспортируемые хуки из `entities` и обращения к провайдерам с соблюдением направления зависимостей: импортировать вышележащие слои нельзя.

Каждый виджет размещается в собственном слайсе `widgets/<Название>` с сегментами `ui`, `model` и `lib`. Размещение компонентов, стилей, типов и логики подчиняется [общим правилам слайса](#код-внутри-слайса).

### Особенности features

Фича — компонент, который решает одну конкретную пользовательскую задачу. Каждый компонент-фича размещается в собственном слайсе с сегментами `ui`, `model` и `lib`, как `features/ChangeTheme` в примере выше.

В фичах разрешены вызовы запросов и использование провайдеров. Запросы подключаются через экспортируемые хуки из `entities`. При обращении к провайдерам сохраняются правила зависимостей: импортировать вышележащие слои нельзя.

Размещение компонентов, стилей, типов и логики подчиняется [общим правилам слайса](#код-внутри-слайса).

### Особенности entities

В `entities` внутри `ui` разрешены директории компонентов: `entities/example/ui/example/Example.tsx`. В них допускаются только файлы `*.ts`, `*.tsx` и стили `*.styles.ts` / `*.styles.tsx`.

В каждой директории компонента допускается не более одного файла стилей, названного как главный компонент: `Example.styles.ts` или `Example.styles.tsx`. Все стили компонентов этой директории выносятся в него.

В `entities/*/ui/**` запрещены запросы и обращения к провайдерам и сторам, в том числе через оборачивающие их хуки. Единственное исключение — хук темы `useTheme`.

В `entities/ui` размещаются только чистые («глупые») компоненты: при одинаковых props и теме отображение одинаково. Компоненты не имеют собственного состояния, меняющего отображение. Оно меняется только при изменении props; исключение — изменение оформления при смене темы через `useTheme`.

Данные и обработчики действий компоненты получают через props, а события передают вызывающему коду через callbacks. Изменения данных, запросы и доступ к состоянию выполняет вызывающий код вне `entities/ui`.

Общие типы сущности размещаются в `model` на уровне слайса: `entities/example/model/example.types.ts`. Хуки и вспомогательная логика размещаются в `lib` на уровне слайса: `entities/example/lib/example.ts`.

## Взаимодействие с сервером

Для взаимодействия с сервером в слайсе сущности по необходимости создаются дополнительные сегменты рядом с `ui`, `model` и `lib`:

- `api` — REST-запросы.
- `receive` — взаимодействия по WebSocket по схеме «запрос–ответ».
- `send` — ответы по WebSocket.

В этих сегментах описываются операции соответствующей сущности.

```text
entities/
└── example/
    ├── getProfile.ts
    ├── api/
    ├── receive/
    ├── send/
    ├── model/
    │   └── example.types.ts
    ├── lib/
    │   └── example.ts
    └── ui/
        └── example/
            ├── Example.tsx
            └── Example.styles.tsx
```

### Структура запросов

Каждый запрос размещается в отдельной директории внутри слайса сущности: `entities/<сущность>/(api|send|receive)/<запрос>/`.

Директория запроса `example` содержит четыре файла:

- `example.ts` — функция запроса и экспортируемый хук TanStack Query.
- `example.types.ts` — типы запроса и ответа.
- `example.validation.ts` — валидационные схемы.
- `example.conversion.ts` — преобразования ответов бэкенда.

Типы конкретного запроса хранятся рядом с ним в `example.types.ts`, общие типы сущности — в её `model`.

```text
entities/
└── company/
    └── api/
        └── example/
            ├── example.ts
            ├── example.types.ts
            ├── example.validation.ts
            └── example.conversion.ts
```

Для `send` и `receive` структура директорий и файлов аналогична.

### Изоляция типов запросов

В `entities` в файлах `*.types.ts`, `*.validation.ts` и `*.conversion.ts` запрещено переиспользовать типы других запросов, даже если их структуры полностью идентичны. Каждый запрос объявляет собственные типы в своём `*.types.ts`; его валидации и конвертации используют эти локальные типы. Правило действует для `api`, `send` и `receive`, включая запросы внутри одного слайса.

Запрет распространяется как на прямое использование типов другого запроса, так и на создание производных типов через алиасы, наследование и utility types (например, `Pick`, `Omit`, `Parameters` и `ReturnType`).

### Функции в файле запроса

В каждом `example.ts` сегментов `api`, `send` и `receive` должны быть две функции:

1. Внутренняя функция запроса — использует транспортный клиент, например `axios`, `httpClient` или `wsProtocolClient`. Не экспортируется из файла.
2. Экспортируемый хук TanStack Query — вызывает внутреннюю функцию запроса через `useQuery` или `useMutation` в зависимости от операции.

### Типизация запросов

В файле типов запроса экспортируются интерфейс параметров `I<НазваниеЗапроса>Payload`, интерфейс исходного ответа бэкенда `API<НазваниеЗапроса>` и тип функции запроса `I<НазваниеЗапроса>`, возвращающей `Promise` с преобразованным ответом.

Тип `I<НазваниеЗапроса>` описывает полный контракт функции: как входной payload, так и преобразованный response в `Promise`.

Пример для удаления нейтральной сущности `record` через `receive` — файл `entities/record/receive/recordDelete/recordDelete.types.ts`:

```typescript
export interface IRecordDeletePayload {
  recordUUID: string;
}

export type IRecordDelete = (payload: IRecordDeletePayload) => Promise<{
  type: 'record.deleted';
  requestId: string;
  payload: {
    recordUUID: string;
  };
}>;
```

Внутренняя функция запроса в `recordDelete.ts` типизируется через `IRecordDelete` и не экспортируется. Преобразование ответа бэкенда из `APIRecordDelete` в формат результата функции выполняется в `recordDelete.conversion.ts`.

Для REST используется тот же подход. Пример файла `entities/record/api/recordDelete/recordDelete.types.ts`:

```typescript
export interface IRecordDeletePayload {
  recordUUID: string;
}

export interface APIRecordDelete {
  record_uuid: string;
}

export type IRecordDelete = (payload: IRecordDeletePayload) => Promise<{
  recordUUID: string;
}>;
```

`APIRecordDelete` описывает исходный ответ бэкенда и используется при его обработке и преобразовании в `recordDelete.conversion.ts`. В этом REST-примере функция возвращает преобразованные данные без WS-обёртки `type`, `requestId`, `payload`.

### Полный цикл запроса

Каждый запрос проходит последовательность: **транспорт → валидация → конвертация → результат**.

1. Внутренняя функция запроса выполняет запрос через транспортный клиент.
2. Полученные данные проверяются схемой из `<запрос>.validation.ts`.
3. Проверенные данные преобразуются функцией из `<запрос>.conversion.ts` в формат приложения.
4. Внутренняя функция возвращает `Promise` с преобразованным результатом, который получает TanStack Query.

Этапы выполняются последовательно через `.then()`. При ошибке валидации конвертация не выполняется. Ошибки транспорта, валидации и конвертации обрабатываются через `.catch()` и пробрасываются дальше, чтобы TanStack Query получил ошибку запроса.

### Именование queryKey

Константа ключа объявляется в файле запроса. Её имя состоит из имени внутренней функции запроса и суффикса `Key`. Строковое значение ключа точно совпадает с именем внутренней функции.

Например, для внутренней функции `companyList`:

```typescript
export const companyListKey = 'companyList';

// В настройках useQuery:
queryKey: [companyListKey]
```

Если результат запроса зависит от параметров, они включаются в `queryKey` после ключа, чтобы различать результаты в кеше, например `[companyListKey, payload]`.
